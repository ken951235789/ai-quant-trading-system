# 資料覆蓋、儲存架構與產品化指南

這份文件用目前的 BTC 15 分鐘 SAC／PPO + Transformer 系統為例，說明資料是否足夠、
PostgreSQL、DuckDB、SQLite 與「加鎖」的差別，以及個人研究專案走到公司級產品時會多出
哪些工程、金融與治理責任。

## 1. 研究標的與下單系統必須是同一份契約

「都是 BTC」仍不代表同一市場。BTC 現貨與 BTC USD-M 永續有不同的價格、手續費、
Funding、槓桿、清算、持倉與下單語意。若模型用永續合約資料學會空頭與 Funding，最後卻
送到現貨，負動作只能賣出持有的 BTC，模型學到的策略沒有被真正執行。

目前主流程固定為：

| 契約維度 | 研究／回測／模擬／下單 |
|---|---|
| Venue | Binance |
| Product | USD-M perpetual futures |
| Instrument | BTCUSDT |
| Quote / margin | USDT |
| Position mode | One-way，signed net position |
| Margin mode | ISOLATED |
| Leverage | 1 至 3 倍，預設 2 倍 |
| Decision interval | 15m 已收盤 K 線 |
| Context intervals | 5m、15m、1h、4h、1d（依模型欄位） |
| Direction | Long、Flat、Short |
| Reversal | 先 reduce-only 平倉，下一根再反向開倉 |
| Protection | Mark Price 停損與停利條件單 |

一致性應該由程式強制，不是靠操作人記得。模型來源若不是 `binance_futures`，即使只在
Testnet 驗證也會被拒絕；舊 Spot 狀態亦不會被算入 Futures 持倉和驗收證據。

## 2. 「資料量」到底在量什麼

資料量不是只有 CSV 幾 GB，至少有六個維度：

1. **時間長度**：涵蓋幾年、幾個牛熊循環。
2. **時間解析度**：1m、5m、15m 或 tick；越細不必然越有資訊。
3. **市場數量**：BTC 單市場，或同時有 ETH、Nasdaq、DXY 等背景市場。
4. **欄位深度**：OHLCV、Funding、OI、Basis、成交方向、Order Book、新聞。
5. **市場狀態覆蓋**：上漲、下跌、盤整、高波動、低流動性、極端事件。
6. **有效獨立樣本**：連續 K 線高度相關，35,000 根 15m K 線不等於 35,000 個獨立實驗。

### 2.1 K 線筆數估算

不考慮缺漏時，一個 24/7 市場每年的理論筆數約為：

| 週期 | 每年筆數 |
|---|---:|
| 1m | 525,600 |
| 5m | 105,120 |
| 15m | 35,040 |
| 1h | 8,760 |
| 4h | 2,190 |
| 1d | 365 |
| 上述全部 | 677,075 |

五年全部週期約 339 萬列。純 OHLCV CSV 常見約 0.1 至 0.3 KB/列，實際大小受 timestamp、
小數位與重複 metadata 影響；若把 200 個特徵都展開成 CSV，單列可能變成數 KB。較合理
的方法是：原始 K 線各週期分開存 Parquet，最後只在 15m 決策索引上做 as-of join，避免把
每個慢週期資料重複展開成大量 CSV。

Order Book 與逐筆成交完全是另一個量級。假設每秒只有 10 筆事件，一天也有 864,000
筆；高峰可能遠高於此。沒有先定義訊號需要的更新頻率、保留期限與壓縮方式，就不應直接
宣稱要永久保存所有深度資料。

### 2.2 市場覆蓋不等於交易很多標的

此系統現在只交易 BTC 是合理的縮小範圍，但仍需要「背景市場覆蓋」：

- BTC 永續本身：OHLCV、成交量、Funding、OI、Basis、Mark/Index Price。
- 執行條件：Spread、預估滑價、資料延遲、交易時段與重大事件 blackout。
- 可選背景：ETH/BTC、Nasdaq、DXY、VIX、ETF 流量；它們是特徵，不是自動取得交易權限。

市場覆蓋的目標是讓訓練、驗證與測試都看過不同 regime，而不是盲目增加幣種。BTC 單標的
模型應先用多段 walk-forward 驗證；若增加其他幣，必須加入 instrument embedding、各市場
成本與流動性規則，不能把所有 K 線當成同一分布。

### 2.3 資料切分的正確觀念

- 依時間排序，禁止 random shuffle 後切 train/test。
- Transformer label 的未來視窗若跨越切分點，要 purge；相鄰樣本還要考慮 embargo。
- Scaler、缺值填補、特徵選擇只能在 train fit，再套到 validation/test。
- 最終 test 只用於一次性估計，反覆看 test 調參會把 test 變成 validation。
- 要保存資料版本、程式 commit、模型參數、seed、套件版本與成本假設，才能重現。

## 3. PostgreSQL、DuckDB、SQLite 各自負責什麼

### 3.1 SQLite

SQLite 是嵌入式關聯式資料庫：整個資料庫通常是一個檔案，不需要另開 database server。
它有交易、索引、unique constraint 和 WAL，適合單機設定、桌面 App、小型 paper state。

限制是「同一時間只能有有限的 writer」。WAL 可讓讀取與寫入較不互相阻塞，但大量背景
程序同時更新訂單、持倉、心跳、Dashboard 查詢時，仍可能遇到 `database is locked`。SQLite
不是沒有鎖，而是鎖的粒度與部署模型較偏單機。

### 3.2 DuckDB

DuckDB 也是嵌入式資料庫，但設計重點是 OLAP 分析：快速掃描大量欄位式資料、Join、聚合，
並能直接查 Parquet。它很適合研究員在單機做特徵分析、回測查詢與報表。

DuckDB 不應當作多個長駐服務共同寫入的交易狀態中心。它擅長「大量讀、批次寫、單一分析
程序」，不是低延遲訂單系統的多 writer 協調器。

### 3.3 PostgreSQL

PostgreSQL 是獨立 server 型資料庫，支援多使用者、多連線、交易、MVCC、row-level lock、
constraint、replication、備份與權限。它更適合公司級交易狀態：orders、fills、positions、
decisions、risk events、model registry 與 audit metadata。

PostgreSQL 不會自動讓程式正確。仍要設計 transaction 邊界、唯一鍵、idempotency key、
isolation level、deadlock retry、connection pool 和 migration。

### 3.4 「加鎖」是在解決什麼

假設 Dashboard 和背景機器人同時讀到 position=0，兩者都決定下 0.01 BTC，最後會變成
0.02 BTC。這叫 lost update / race condition。鎖的目的，是讓「讀狀態、驗證、更新」成為
不可被另一 writer 插入的臨界區。

常見鎖有：

- **檔案鎖**：本專案目前 CSV append 使用 `.lock` 排他檔；一次只允許一個 writer，程序
  異常留下的舊鎖會在期限後清理。它適合本機過渡，不適合跨多台主機。
- **SQLite transaction / WAL**：由 SQLite 管理資料庫檔鎖；要設定 busy timeout，交易保持短。
- **PostgreSQL row lock**：`SELECT ... FOR UPDATE` 只鎖要更新的 position row；其他商品仍可並行。
- **Advisory lock**：用策略 ID 或帳戶 ID 取得邏輯鎖，保證同一策略同時只有一個 rebalance。
- **Optimistic lock**：position 帶 `version`，更新時要求舊 version 相同；失敗代表狀態已被別人改過。

鎖不等於原子下單。交易所是一個外部系統，資料庫 transaction 無法包住 Binance 撮合。
正確做法是 Saga / state machine：先建立唯一 decision 與 client order id，送單後依 User Data
Stream 或 query order 對帳，任何 timeout 都以同一 id 查詢，不能直接重送。

## 4. 建議的儲存演進

### 現在：單機研究與 Testnet

```text
Raw K 線 / 衍生資料   CSV（下一步改 Parquet）
研究查詢              Pandas（下一步加 DuckDB）
交易狀態              JSON + CSV + 排他檔案鎖
模型成品              版本化資料夾 + metadata
```

### 下一階段：可靠的個人服務

```text
Raw / Feature          partitioned Parquet
Research / Backtest    DuckDB 查 Parquet
Orders / Fills / State SQLite WAL（單一 writer service）
Dashboard              只透過 service API，不直接改資料檔
```

### 公司級

```text
Historical lake        Object Storage + Parquet
Research analytics     DuckDB / Spark（依資料量）
Trading source of truth PostgreSQL primary + backup / replica
Realtime transport     WebSocket ingestion + message queue（有需要才加入）
Metrics / logs / traces Observability stack
Secrets                KMS / Secret Manager，不放 .env 或使用者電腦明文
```

PostgreSQL 最少應有 `instruments`、`bars`、`model_versions`、`predictions`、`decisions`、
`orders`、`fills`、`positions`、`risk_events`、`reconciliation_runs`。`client_order_id`、交易所
trade id 與 `(venue, symbol, interval, open_time)` 必須有 unique constraint。

## 5. 個人專案、商品與公司規格的差別

### 個人研究專案

重點是問題定義、無洩漏資料、可重現實驗、合理回測與清楚限制。可以由一個人手動維運，
允許本機檔案和較低 SLA，但不能把回測獲利說成實盤保證。

### 可交付商品

除了策略，還要有安裝、升級、設定驗證、錯誤訊息、使用者權限、資料來源授權、API 版本
相容、備份還原、隱私條款、支援流程與安全更新。若替客戶保管 API key 或代下單，法律、
資安與責任邊界會大幅增加；法規取決於地區與商業模式，需要正式法律意見。

### 公司級交易系統

公司會問的不只是「能不能跑」，而是：

- **正確性**：訂單狀態機、部分成交、取消、重送、重啟後能否完全對帳。
- **可用性**：SLO、故障偵測、降級模式、RTO/RPO、災難復原演練。
- **風險隔離**：交易前限制、交易中監控、交易後核對、獨立 kill switch。
- **安全**：最小權限、key rotation、KMS、RBAC、稽核、依賴與供應鏈掃描。
- **資料治理**：schema、lineage、quality check、時區、企業行動、版本與保存政策。
- **模型治理**：模型 registry、核准流程、champion/challenger、drift、rollback、可解釋決策。
- **可觀測性**：metrics、structured logs、distributed trace、告警與 on-call runbook。
- **變更治理**：code review、CI/CD、migration、staging、canary、incident postmortem。
- **商業與合規**：資料授權、交易所條款、客戶適合度、聲明與地區法規。

公司規格最大的差別是「每個失敗模式都有 owner、偵測方式、處置步驟與證據」，而不是多裝
幾個模型。

## 6. 你需要補的理論與知識

### 金融與市場微結構

- arithmetic/log return、PnL accounting、mark-to-market。
- 永續合約 Funding、Basis、Mark Price、Index Price、初始/維持保證金與清算。
- bid/ask、maker/taker、spread、slippage、queue position、partial fill。
- position sizing、risk of ruin、drawdown、VaR/Expected Shortfall 的限制。
- Sharpe、Sortino、Calmar、Profit Factor、Expectancy 與 turnover。

### 統計與量化研究

- stationarity、autocorrelation、heteroskedasticity、regime shift。
- sampling bias、survivorship bias、look-ahead、data leakage。
- multiple testing、selection bias、backtest overfitting。
- walk-forward、purged time-series split、embargo、bootstrap confidence interval。
- 淨報酬的成本敏感度與 Monte Carlo / stress test。

### ML、Transformer 與 RL

- normalization、sequence window、label horizon、attention mask、calibration。
- MDP 的 state/action/reward/transition，partial observability 與 non-stationarity。
- SAC 的 actor、twin critic、entropy、replay buffer、off-policy；PPO 的 on-policy clipping。
- reward hacking、sim-to-real gap、offline evaluation 與 distribution drift。
- 模型輸出與硬風控分權：模型不能自行放寬槓桿、損失上限或 kill switch。

### 軟體與資料工程

- Python typing、pytest、property-based test、profiling、async I/O。
- REST、WebSocket、heartbeat、reconnect、sequence number、backpressure。
- SQL、transaction、MVCC、index、lock、migration、backup/restore。
- state machine、idempotency、event-driven architecture、Saga、outbox pattern。
- Docker、CI/CD、Linux service、structured logging、metrics、tracing。
- secrets、TLS、least privilege、threat modeling、dependency/SBOM scanning。

## 7. 如何把它變成履歷專案

不要寫「做出保證獲利 AI」。把專案描述成一個可驗證、fail-closed 的 BTC 永續量化研究與
Testnet 執行平台，並提供實際測試數、資料範圍、延遲與故障處理證據。

建議履歷成果必須能展示：

1. 一張架構圖：ingestion → feature → Transformer → SAC → risk → execution → reconciliation。
2. 一份 data contract：symbol、venue、interval、timezone、schema 與品質規則。
3. 一份無洩漏 walk-forward 報告，含 fee/slippage/funding 壓力測試。
4. 一個 Testnet demo：多空、reduce-only 反手、保護單、timeout 查單與重啟對帳。
5. 一組自動測試與 CI 結果，尤其是風控 invariant 與失敗案例。
6. 一份 incident runbook：WebSocket 中斷、DB 鎖、未知訂單、模型缺檔如何處理。
7. 一份限制清單：尚未完成與不能宣稱的能力。

履歷句型可以寫成：

> Built a BTCUSDT USD-M perpetual research and Testnet execution platform in Python,
> aligning multi-timeframe Transformer/SAC signals with signed futures exposure,
> reduce-only reversal, exchange-native protection orders, idempotent order recovery,
> and restart reconciliation; validated by an automated test suite and walk-forward reports.

量化數字只能填實際量測值，例如測試數、涵蓋年份、資料列數、P95 decision latency、重啟
恢復時間與 Testnet 成功輪次，不能把未發生的收益寫進去。

## 8. 建議學習順序

1. **第一個月**：永續合約會計、PnL、Funding、清算；SQL transaction 與索引。
2. **第二個月**：時間序列切分、walk-forward、成本模型與統計顯著性。
3. **第三個月**：訂單狀態機、WebSocket user stream、idempotency 與重啟對帳。
4. **第四個月**：PostgreSQL schema/migration、Docker、CI、metrics、alerts、runbook。
5. **之後**：SAC/PPO 診斷、Transformer calibration、drift 與 champion/challenger。

最適合你現在開始的實作題目是：把本地交易 source of truth 搬到 PostgreSQL、用 DuckDB
直接查 partitioned Parquet，並完成 Futures User Data Stream 的事件驅動訂單狀態機。這三項
會讓專案從「有模型的 App」更接近真正的 Quant Developer / Trading Systems 履歷作品。
