# 統一事件重播與故障注入研究

更新日期：2026-09-20

## 研究問題

歷史資料直接以 DataFrame 進入回測，而即時資料由 WebSocket callback 更新時，兩條資料路徑
可能產生不同行為。本研究驗證歷史與即時來源是否能共用同一份事件契約、順序規則、去重
機制與 checkpoint 語意。

```text
歷史 OHLCV CSV ──> HistoricalMarketEventSource ─┐
                                                 ├─> MarketEventBus
Binance WebSocket ─> BinanceKlineUpdate ─────────┘       │
                                                         ├─ 去重
                                                         ├─ 順序檢查
                                                         ├─ 缺 K 偵測
                                                         └─ Consumer
                                                              │
                                                              ├─ 即時市場緩衝
                                                              └─ 歷史 DataFrame 重建
```

同一根 K 線的 event ID 只由交易所、標的、週期與開盤時間決定，不包含 REST、CSV 或
WebSocket 來源，因此補漏資料和即時資料不會重複觸發模型。

## 執行方式

```powershell
python scripts\run_replay_research.py `
  --input "data\raw\crypto\binance_futures\ohlcv\ohlcv_crypto_binance_futures_BTC-USDT_15m_latest.csv" `
  --limit 500 `
  --output-root "data\research\event_replay"
```

每次實驗會建立獨立資料夾：

| 檔案 | 用途 |
|---|---|
| `research_report.md` | 研究問題、假說、結果、限制與重現方式 |
| `research_manifest.json` | 資料 SHA、Git、Python、套件版本與參數 |
| `fault_results.csv` | 每個故障情境的預期與實際結果 |
| `reconstructed_events.csv` | 由 MarketEvent consumer 重建的 OHLCV |
| `checkpoints/` | 中斷與 consumer 崩潰的續傳位置 |
| `artifact_manifest.json` | 所有研究成品的 SHA-256 完整性清單 |

## 故障模型與通過條件

| 情境 | 注入方式 | 通過標準 | 系統意義 |
|---|---|---|---|
| Baseline | 無故障依序重播 | 輸入與唯一輸出筆數一致 | 基本資料契約正確 |
| 重複事件 | 同一 event ID 投遞兩次 | Consumer 只保存一次 | REST 與 WebSocket 重疊時不重複決策 |
| 傳輸中斷 | 在中間事件前中止 | 從 checkpoint 續傳且零遺失 | 斷線後可安全恢復 |
| Consumer 崩潰 | 指定事件第一次處理失敗 | checkpoint 不前進，重啟重試成功 | 寫入失敗不跳過行情 |
| 亂序事件 | 交換相鄰 K 線 | 偵測時間倒退並 fail closed | 舊行情不能覆蓋新決策 |
| 缺 K | 移除中間一根 K 線 | 偵測週期間隔缺口 | 補漏前不允許模型判斷 |
| 損壞 OHLCV | 令 high 低於 open/close | 進入 consumer 前拒絕 | 錯價不能污染特徵與訂單 |

## 可重現性判準

同一輸入檔、Git commit 與參數再次執行時，`research_manifest.json` 的 `result_sha256`
應相同；產生時間、牆鐘秒數與輸出資料夾名稱可以不同。工作目錄有未提交修改時，manifest
會標記 `git_dirty=true`，表示該次結果無法只靠版本標籤完整重建。

## 研究能力與驗證矩陣

| 領域 | 關鍵問題 | 本研究的驗證證據 |
|---|---|---|
| 機率統計 | 單次結果是否具有統計意義 | 後續以多區段、信賴區間與 Bootstrap 評估 |
| 時間序列 | 如何阻止未來資料與隨機切分洩漏 | 事件時間排序、已收盤資料與 Walk-forward |
| 市場微結構 | 訊號價與成交價有何差異 | Spread、Slippage、Funding 與 Order Book 欄位 |
| 事件驅動 | 重送與重啟如何保持一致 | 確定性 event ID、冪等 consumer 與 checkpoint |
| 資料庫 | 跨程序如何避免重複事件 | PostgreSQL 唯一鍵、transaction 與事件投影 |
| 可靠性工程 | 系統在故障時是否 fail closed | 中斷續傳、亂序、缺 K 與損壞資料實驗 |
| 資安 | 研究成品是否可驗證且不含秘密 | 憑證隔離、SHA-256、依賴掃描與權限邊界 |
| 科學方法 | 結果能否被重現與否證 | 輸入 SHA、Git commit、參數、限制與結果摘要 |

## 已知限制

- 離線事件重播不等同於真實交易所網路環境。
- 目前沒有模擬作業系統斷電、磁碟毀損或交易所全區故障。
- 單程序 Event Bus 的去重不能取代 PostgreSQL 跨程序唯一鍵。
- exactly-once 是端到端性質，consumer 仍必須以 event ID 保持冪等。
