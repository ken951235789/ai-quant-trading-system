## 推甄報告建議架構

建議使用 8 至 12 頁，不要把完整 README 原封不動貼入報告。

1. **研究動機**：市場非平穩、成本與資料洩漏為什麼讓 AI 交易困難。
2. **研究問題**：Transformer 是否有樣本外訊號；SAC 是否能把訊號轉成扣成本後收益。
3. **系統方法**：資料、特徵、Transformer、SAC、固定風控與執行層流程圖。
4. **實驗設計**：時間切分、cross-fit、多 seed、基準、成本與 final holdout。
5. **結果**：同時呈現正面與負面結果，不只展示最好 seed。
6. **失敗分析**：短週期訊號弱、換手成本、SAC 偏空手與市場 regime 漂移。
7. **工程驗證**：單元測試、故障注入、斷線恢復、重複事件與 Kill Switch。
8. **限制與後續工作**：資料覆蓋、統計檢定、paper trading 時間與 Champion 條件。

## 最值得補強的研究產出

1. 以公開、可重新下載的資料重跑一組固定實驗，保存資料雜湊與完整命令。
2. 製作 `Transformer-only / SAC-only / Transformer+SAC / 加風控` 四組消融表。
3. 報告多 seed 平均值、標準差、信賴區間，不只報告單一最佳數字。
4. 加入 regime 分層結果：趨勢、盤整、高波動與低波動各自表現。
5. 累積至少數週到數月的 Testnet／模擬倉 forward test，與歷史回測比較漂移。
6. 錄製 2 至 3 分鐘 Demo：資料進入、模型決策、風控否決、稽核紀錄與安全停止。

## 面試前應真正理解的知識

- **時間序列**：stationarity、autocorrelation、rolling/expanding window、concept drift。
- **統計驗證**：selection bias、multiple testing、bootstrap、信賴區間與基準比較。
- **Transformer**：self-attention、位置資訊、多任務 loss、mask、uncertainty 與校準。
- **SAC**：MDP、state/action/reward、actor-critic、entropy、off-policy replay 與 Q overestimation。
- **量化交易**：PnL、Sharpe、Sortino、最大回撤、turnover、funding、滑價與強平。
- **系統工程**：idempotency、event ordering、checkpoint、reconciliation、observability。
- **研究倫理**：不能用測試集調參、不能把 reward 當收益、不能承諾未來獲利。

## 教授可能追問

### 為什麼不用準確率最高的模型直接交易？

方向準確率沒有包含報酬幅度與成本。模型即使猜對較多次，也可能在少數大行情中虧損，或
因高換手被成本吃掉，因此必須評估扣成本後期望值與回撤。

### 為什麼 Transformer 正、SAC 卻負？

Transformer 的某個 horizon 有方向資訊，不代表 SAC 能穩定決定曝險。SAC 仍可能受到
reward、動作語意、換手、訓練資料覆蓋與 regime 漂移影響，所以需要 cross-fit 與消融。

### 為什麼保留失敗結果？

負面結果證明品質閘門真的會拒絕不合格模型，也讓後續假設可以被驗證；刪除失敗實驗反而
會造成 selection bias，降低研究可信度。

## Star 與推甄的關係

真實 Star、Issue 或外部貢獻能證明作品可讀且有人關注，但不應成為主證據。對推甄更重要的
排序通常是：你能完整解釋的方法與決策、可重現結果、個人貢獻、程式品質、教授或專題老師
的推薦，以及與申請實驗室方向的連結。

最好的使用方式是把 GitHub 當作證據庫：報告負責敘事，README 提供入口，測試與 Commit
證明工程歷程，Release 固定審查版本，研究結果文件則支持你的結論與限制。
