# 統一事件重播、故障注入與推甄知識地圖

更新日期：2026-09-01

## 這個模組解決什麼

過去歷史資料直接以 DataFrame 進入模擬交易，即時資料則由 WebSocket callback 更新緩衝，
兩者可能出現「回測正常、即時行為不同」。現在兩條路徑都先轉成 `MarketEvent`：

```text
歷史 OHLCV CSV ──> HistoricalMarketEventSource ─┐
                                                 ├─> MarketEventBus
Binance WebSocket ─> BinanceKlineUpdate ─────────┘       │
                                                         ├─ 去重
                                                         ├─ 順序檢查
                                                         ├─ 缺 K 偵測
                                                         └─ Consumer
                                                              │
                                                              ├─ 即時市場緩衝
                                                              └─ 歷史 DataFrame 重建
```

同一根 K 線的 event ID 只由交易所、標的、週期與開盤時間決定，不包含 REST、CSV 或
WebSocket 來源，因此補漏資料和即時資料不會重複觸發模型。

## 執行研究

```powershell
cd D:\AIQuantTradingSystem
python scripts\run_replay_research.py `
  --input "data\raw\crypto\binance_futures\ohlcv\ohlcv_crypto_binance_futures_BTC-USDT_15m_latest.csv" `
  --limit 500 `
  --output-root "data\research\event_replay"
```

每次會建立獨立資料夾，內含：

| 檔案 | 用途 |
|---|---|
| `research_report.md` | 研究問題、假說、結果、限制與重現方式 |
| `research_manifest.json` | 資料 SHA、Git、Python、套件版本與參數 |
| `fault_results.csv` | 每個故障情境的預期與實際結果 |
| `reconstructed_events.csv` | 由 MarketEvent consumer 重建的 OHLCV |
| `checkpoints/` | 中斷與 consumer 崩潰的續傳位置 |
| `artifact_manifest.json` | 所有研究成品的 SHA-256 完整性清單 |

## 故障實驗定義

| 情境 | 注入方式 | 通過標準 | 對實盤的意義 |
|---|---|---|---|
| Baseline | 無故障依序重播 | 輸入與唯一輸出筆數一致 | 基本資料契約正確 |
| 重複事件 | 同一 event ID 投遞兩次 | Consumer 只保存一次 | REST 補漏與 WebSocket 重疊不重複交易 |
| 傳輸中斷 | 在中間事件前中止 | 從 checkpoint 續傳且零遺失 | 斷線後可安全恢復 |
| Consumer 崩潰 | 指定事件第一次處理失敗 | checkpoint 不前進，重啟重試成功 | 寫入或模型程序失敗不跳過行情 |
| 亂序事件 | 交換相鄰 K 線 | 偵測時間倒退並 fail closed | 避免舊行情覆蓋新決策 |
| 缺 K | 移除中間一根 K 線 | 偵測週期間隔缺口 | 先 REST 補漏再允許模型判斷 |
| 損壞 OHLCV | 令 high 低於 open/close | 進入 consumer 前拒絕 | 防止錯價污染特徵與訂單 |

## 可重現性的判斷

同一個輸入檔、相同 Git commit、相同參數執行時，`research_manifest.json` 的
`result_sha256` 應相同。時間戳、牆鐘執行秒數及輸出資料夾名稱可以不同。

目前工作目錄含有尚未提交的修改時，manifest 會標記 `git_dirty=true`。推甄提交前應建立
乾淨 commit 和版本標籤，否則教授無法只靠 commit 完整重建結果。

## 推甄應掌握的知識

| 領域 | 你應該掌握什麼 | 為什麼需要 | 建議在本專案完成的練習 | 口試要能回答 |
|---|---|---|---|---|
| Python | dataclass、型別、例外、迭代器、thread lock | 事件核心與背景程序都依賴它 | 解釋 `MarketEvent` 為何不可變、Bus 為何加鎖 | 多執行緒和多程序有何不同？ |
| 資料結構 | Queue、Hash、LRU/容量限制 | 去重不能讓記憶體無限成長 | 說明 event ID 與 `dedup_capacity` | Hash 碰撞與記憶體取捨是什麼？ |
| 機率統計 | 期望值、變異數、信賴區間、Bootstrap | 單次回測報酬沒有統計意義 | 對多段回測計算信賴區間 | 正報酬是否等於有統計優勢？ |
| 假設檢定 | p-value、效果量、多重檢定 | 測很多策略後挑最好會過度樂觀 | 記錄策略嘗試數並修正顯著水準 | Data snooping 是什麼？ |
| 時間序列 | 非平穩、自相關、異方差、regime | 金融資料不是 IID | 畫 ACF、滾動波動與 regime | 為何不能隨機切分 K 線？ |
| 實驗設計 | 假說、基線、控制變因、消融實驗 | 讓結果可反駁且可比較 | 分別移除 Transformer、Funding、成本 | 你的研究貢獻如何被證偽？ |
| 市場微結構 | Bid/Ask、Spread、Slippage、部分成交 | 訊號價不等於成交價 | 比較 maker/taker 與不同滑價 | 為何短線策略對成本特別敏感？ |
| 永續合約 | Funding、Mark Price、保證金、強平 | BTC Futures 的主要風險來源 | 壓測 1～3 倍槓桿與極端跳價 | Mark Price 和 Last Price 差在哪？ |
| 風險管理 | Position sizing、回撤、日損、CVaR | 獲利模型仍可能破產 | 量測各風控對報酬與存活率影響 | 風控應在模型內還是模型外？ |
| 強化學習 | MDP、PPO、SAC、Actor-Critic、Entropy | 理解交易員模型的行為來源 | 解釋 State/Action/Reward | PPO 與 SAC 的資料效率差異？ |
| Transformer | Attention、位置編碼、mask、multi-task | 理解分析師模型如何使用序列 | 畫出輸入張量與預測頭 | 如何防止 Transformer 看見未來？ |
| 事件驅動 | Producer、Consumer、Event sourcing | 統一歷史與即時行為 | 從 CSV 和 WebSocket 建出相同 ID | 為何不用 callback 直接交易？ |
| 傳輸語意 | At-most/at-least/exactly-once、冪等 | 網路重試一定可能重複 | 讓 consumer 以 event ID 去重 | Exactly-once 為何通常是端到端性質？ |
| 資料庫 | ACID、索引、唯一鍵、隔離層級 | 訂單與成交不能只靠 CSV | 解釋 PostgreSQL event projection | unique constraint 如何防止重複成交？ |
| 分散式一致性 | timeout、重試、對帳、狀態機 | 不知道下單結果時不能盲目重送 | 模擬 API timeout 後查單 | Unknown order state 應如何處理？ |
| 可靠性工程 | RPO、RTO、SLO、熔斷、Watchdog | 長期常駐一定會遇到故障 | 量測重連與資料庫恢復時間 | 可接受遺失多少資料、停機多久？ |
| 故障注入 | Fault model、預期不變量、恢復驗證 | 主動證明系統不是只在順境可用 | 擴充磁碟滿、DB 重啟實驗 | 測試失敗和實驗失敗如何區分？ |
| 可觀測性 | Metric、Log、Trace、告警 | 出問題時必須能定位 | 定義延遲、gap、duplicate 指標 | p50/p95/p99 各代表什麼？ |
| 資安 | 最小權限、TLS、秘密、SBOM、簽章 | API Key 洩漏會直接造成資產風險 | Testnet/Live Key 分離與 IP 白名單 | SHA-256 為何不等於來源可信？ |
| 科研倫理 | 限制、負面結果、不可保證獲利 | 推甄重視可信度而不是宣傳 | 保留失敗實驗與限制章節 | 回測好看時有哪些替代解釋？ |

## 建議學習順序

1. Python 型別、測試、Git、SQL 與 Docker。
2. 報酬、風險、時間序列、交易成本與市場微結構。
3. 事件驅動、冪等、狀態機、checkpoint 與故障恢復。
4. 機器學習資料洩漏、Walk-forward、Bootstrap 與多重檢定。
5. Transformer、PPO/SAC、Safe RL 與模型治理。
6. 可觀測性、資安、部署與研究報告寫作。

推甄時應把這套系統描述為「可重現、可故障驗證的 AI 交易研究平台」，不是保證獲利的商品。
